## 一、关于“Data Infra 是什么”——定义层面的补充

你列的三块（存储、获取、管理）是必要的，但可以更精确地抽象为四个“永恒功能”：

1. **存储**（持久化、可靠性、空间成本）
2. **计算**（对数据的变换、聚合、训练、推理）
3. **流转**（数据的移动、复制、实时/批量同步）
4. **治理**（元数据、质量、血缘、安全、合规）

如果参考湖仓一体的文章，你会发现它本质上是将“计算”与“存储”在架构层面解耦，并在“治理”层统一元数据和权限。这对 AI 时代尤其关键，因为AI 的两大工作流——**训练**（大规模离线吞吐）和**推理**（低延迟在线访问）——天然要求存算分离，且要求治理层能同时理解结构化表、非结构化文件和模型产出物。  
因此，建议你把 Data Infra 定义扩充为：**支撑数据全生命周期（采集、存储、处理、流动、消费）的底层系统，核心目标是让数据可发现、可信赖、可高效转化为决策/模型价值。**

## 二、AI 时代 Data Infra 的“变与不变”——第一性原理分析

你的分类“不变的是需要存储、计算、管理，形态会变”触及了本质，但还需向下挖一层，找到**驱动物理形态变化背后不变的经济规律**。

### 1. 先说不变的底层原则（这些是值得投入的地方）

从第一性原理看，数据和计算永远受制于三个物理/经济约束：

- **光速与距离**：数据离计算越近，延迟越低 → 缓存/分层存储永远存在。
- **香农熵与压缩**：数据冗余越高，存储和传输成本越低 → 列存、编码、压缩算法永远是基础。
- **阿姆达尔定律与并行度**：数据处理加速取决于可并行部分，且受串行瓶颈限制 → 分布式计算框架和分区算法本质稳定。

由此推导，**Data Infra 中真正不变、或者变化极慢的“基座”** 是：

- **开放、自描述的不可变数据格式**（如 Parquet、Arrow IPC）：它们是“数据的汇编语言”，无论上层是 SQL 还是 LLM，最终都要落到高效序列化上。
- **基于不可变事实的存储层**（对象存储、版本化表格式如 Iceberg/Delta/Hudi）：提供时间旅行、快照隔离、ACID，这是所有上层复现性的根基。
- **元数据与治理体系**（统一 catalog、血缘、权限）：AI 模型的可信、可解释、可审计，高度依赖这一层。消费者从人变成 Agent 后，**自动化的数据发现与合规**反而更重要。
- **存算分离的架构**：计算资源弹性伸缩，存储低成本无限扩展，这个方向不会逆转。

这些领域的变化相对缓慢，且更多是渐进式工程优化，适合长期押注。

### 2. 再看你列的“变化点”——哪些判断精准，哪些需要修正

#### a. 接口与语义变化（“AI 是主要生产和消费者”）
你说的“接口发生变化”非常核心。传统接口是 SQL 和 DataFrame API，面向人类分析师；AI 时代主流消费者变为：
- 训练框架（PyTorch/TF）直接读数据 → 需要**极致的扫描吞吐**和**可复现的随机访问**。
- LLM/Agent 通过工具调用（function calling）查询 → 需要**自然语言到结构化查询**的可靠翻译，及**语义化的元数据层**（列注释、指标定义、业务上下文）。
- 向量检索与多模态理解 → 需要**embedding 向量**作为一等公民，存储在向量库或 Lakehouse 中的向量索引。

这里“AI 能理解的关系”不是一种魔法，而是**可机器解释的语义模型**：包括实体-关系图、特征定义、度量标准、业务术语表。这一层会从“锦上添花”变成“基础设施硬需求”。  
你的直觉是对的，但需进一步明确：**变化发生在“语义翻译层”和“呈现层”，而非底层物理格式**。

#### b. 数据量与 QPS 的变化
- **总量必然变大**，但增量更多来自**非结构化原始数据**（日志、图像、视频、文档）和**合成数据**。训练需要海量多样化数据，推理也需要大量上下文（RAG）。
- **QPS 不一定只靠 Agent 数量暴增**。Agent 调用数据往往通过工具层，可能产生大量小查询（元数据搜索、点查）和少量复杂分析。但推理场景对**P99 延迟极度敏感**，因为 Agent 等待结果的超时时间很短。  
  你提到的 “cold start” 可能指 **RAG 知识库的初始化加载**或**模型服务的首次数据拉取**，这需要用预热、分层缓存来解决，属于“近推理侧计算”范畴。
- 真正值得重视的：“单次查询耗时”的 **SLA 结构会完全改变**。不再是人类容忍几十秒的报表，而是机器对机器（M2M）的亚秒级要求，这会推动**实时特征工程、流批一体、预计算物化视图**成为标配。

#### c. 不同模态数据统一处理
你的判断“结构化和半结构化基本没有区别”很准，在列式存储+嵌套类型（如 Parquet/Arrow 的 struct, list, map）下，两者可以统一。  
对非结构化数据，**怎么使用**现在收敛到一个核心模式：
- **转化为结构化描述**（通过视觉模型、语音识别、文档解析抽取标签、摘要、embedding），然后把描述和原始文件一起管理。
- **Embedding 就是非结构化数据的“计算型索引”**，向量检索本质是为非结构化内容建索引。
- 所谓“通用计算”更合适的做法，不是让 SQL 强行处理图片，而是让 Lakehouse 能**在同一个治理框架下管理表、文件、模型资产，并提供多语言计算引擎**（SQL + Python + 向量搜索）。  
  你缺的一环是：**特征存储（Feature Store）**——它是结构化/非结构化处理后的统一供给层，把训练和推理的特征口径对齐。

#### d. 近推理侧的计算与算力融合
这是非常重要的点。数据 Infra 的瓶颈正从“存不下”变成“**供不及**”——GPU 等待数据。因此：
- **数据预处理流水线需要向 GPU 亲和**（如 RAPIDS、零拷贝 Arrow 到 GPU）。
- **推理侧缓存和轻量级特征服务**会贴近推理集群，形成“数据面网格”，供 Agent 低延迟查询。
- 算力融合不止是 CPU+GPU，还包含 DPU/SmartNIC 做数据解压、过滤，释放主机资源。但这对 Data Infra 提出新要求：**存储格式和传输协议需要支持向量化下推、列裁剪**，这恰恰又回到了开放格式和 Arrow 的设计，是不变的部分。

## 三、用经济学视角强化“在不变处投入”的策略

你问 Data Infra 怎么做，结合经济学，可抽象为一个“**成本-收益-风险**”权衡：

### 1. 识别“互补品”与“必需品”
AI 模型和数据是**互补品**：模型越好，数据需求越大，高质量数据变得稀缺。因此，**确保数据的产权、质量、血缘的 Infra**（治理层）会成为必需品。即使上层的分析工具、模型框架快速迭代，没有可信的数据基础，所有上层建筑都会崩塌。  
→ **投入建议**：聚焦开放标准下的治理与元数据层（Unity Catalog、开放 lineage），这是变化最少、需求最刚性的一块。

### 2. 降低交易成本
Coase 定理在企业内部数据应用：如果数据发现、理解、获取的交易成本够低，数据就能流向最有价值的用途。AI 进一步放大了这种需求——模型训练和推理需要跨部门、跨模态的数据拼图。  
→ **不变的高价值区**：统一语义层、自动化发现/探查、数据契约（data contract），这能让 AI Agent 像市场中的理性人一样高效获取数据，减少半衰期极短的定制管道开发。

### 3. 实物期权思维
在上层应用（如特定的 AI 查询引擎、向量数据库）方向尚不确定时，应优先投资那些能降低后续选择成本的**基础期权**：
- 把数据按**开放格式、标准 catalog** 存储，未来可以无缝切换到任何新引擎。
- 把非结构化资产以统一模型管理（Iceberg 的表格式正在扩展到文件列表/元数据），这样以后是向量库还是全文索引都不怕。
- 这部分正是你说的“变化更少的地方”。

## 四、你现有清单可能存在的问题与直接补充

1. **“易用发生了变化，语义需要以 AI 能理解的关系去呈现”**  
   需要避免一个误区：不是让人类放弃现有语义，而是为 AI 额外构建一层**机器可读的语义层**（技术词汇：语义模型、知识图谱、数据编织）。这层需要跟随业务快速迭代，**属于变化较快的地方**，不适合作为最底层的“不变”投入，但可以作为中间层的战略投资。

2. **“非结构化数据主要怎么使用”**  
   建议补上：非结构化数据的价值释放高度依赖**预处理流水线（embedding、chunking、摘要）**，因此 Data Infra 必须提供**弹性、可观测的流水线编排能力**，并且处理好“原始文件”和“衍生物（向量、文本片段）”之间的血缘和同步失效问题。这是数据工程一个确定的新痛点。

3. **“近推理侧的计算”**  
   这里你直觉有道理，但需补充：**特征工程的在线/离线统一**是最硬的骨头。离线训练用一大套特征，线上推理需要完全一致但延迟极低的特征服务。这要求 Feature Store 不仅是字典服务，还要有**时点正确（point-in-time correct）**的存储和回放能力。这是 AI Data Infra 不变的核心组件，却常常被忽略。

4. **完全没提到但至关重要的“不变”**  
   - **数据可复现性**：模型实验要求任意时刻都能回放当时的全量数据状态。时间旅行、快照隔离、数据版本控制是刚需。  
   - **安全与隐私的原子化**：AI 训练可能会跨租户混合数据，差分隐私、联邦学习、细粒度访问控制将嵌入存储层，而非外部补丁。  
   - **成本可观测性**：算力宝贵，哪些数据被频繁使用、哪些是“冷数据但高价值”、存储和查询的边际成本，需要精细计量，以形成内部经济闭环（数据计费、退订）。

## 五、总结：一个更聚焦的“不变”投资清单

结合第一性原理和经济学，你可以把这些定为“变化最少、最值得深耕”的 Data Infra 内核：

1. **通用开放数据表示层**：Arrow/Parquet 生态，跨语言零拷贝。
2. **不可变、版本化的表格式与文件组织**：Apache Iceberg 等，为一切数据（表、文件、流）提供统一抽象。
3. **联邦化、可互操作的治理目录**：承载业务语义、血缘、权限，成为 AI Agent 检索数据的“宪章”。

5. **时点一致的流批一体引擎**：用来构建特征和物化视图，保证训练和推理的口径统一。

上层哪些 Agent 框架、哪种自然语言查询接口、用哪种向量数据库，都会快速演化；但底层的“数据比特表示 + 不可变事实 + 可信语义”这套宪法性存在，变化极慢，且长期定价权最高。你在这个方向投入，是符合第一性原理的安全且高价值的策略。

## 逐层审视与校准

### 第 1 层：物理存储层（开放数据表示层）
**你的描述**：通用的开放数据表示层，如 Parquet、Arrow 等，跨语言零拷贝。  
**评价**：完全正确。但需注意“物理存储层”这个名词可能引起混淆——Parquet 是序列化格式，Arrow 更多是内存中的标准列式表示，严格说它们属于**数据表示层/序列化层**，还不是物理介质（磁盘、SSD、对象存储）。  
**建议微调**：将这一层称为**“标准数据表示层”**，它定义了数据在磁盘和网络上如何编码，以及如何在内存中高效交换。它们是整个栈的“汇编语言”，是变化最慢的底座。  

**不变性支撑**：Arrow 的零拷贝、跨语言特性，让上层无论是 Pandas、Spark 还是 PyTorch 都能直接操作，减少了数据拷贝的“交易成本”。

### 第 2 层：物理层的组织与抽象层（表、文件、流、特征）
**你的描述**：在物理存储层上做了统一抽象，提供表、文件、流、feature 等接口，比如 Iceberg，支持 time travel 等语义，用于 A/B test 或时间回溯。  
**评价**：这个概括非常精准，而且你直接把“feature”纳入这一层抽象，眼光超前。传统认知中表格式（Iceberg/Delta/Hudi）只管表，但 AI 时代的必然趋势是用同一套版本化、快照隔离、ACID 语义去管理**所有数据资产**：结构化表、半结构化文件集合、流数据，以及**特征数据**、模型输入/输出数据集。

**需要校准和补充的地方**：
- Iceberg 目前主要针对“表”抽象，但它通过 **Object Store + Manifest** 机制，天然可以管理大批量文件的版本集合。未来会扩展到更通用的数据集抽象（Iceberg 社区已经在讨论视图、物化视图、甚至特征工程）。
- 你说“统一抽象”很对，但**接口不同**：表用 SQL，文件集合用 Python/DataLoader，流用消息队列协议。这一层的价值在于**事务性的元数据管理层**（manifest, snapshot），而不一定是统一所有访问模式。
- 时间旅行不只用于 A/B 测试，更核心的是**可复现性**：模型训练需要精确回到某个时间点的数据集状态，这对于金融、医疗等监管行业是“必需品”，而非“功能点”。

**结果**：第 2 层本质是 **“不可变事实日志的元数据层”** 。它决定了上层能否实现数据版本控制、增量处理、时光回溯。这是 AI 时代 Data Infra 最关键的不变核心之一。

### 第 3 层：治理与语义层（Catalog、权限、血缘、语义）
**你的描述**：数据管理，涉及 Catalog、权限、血缘等，跨地域，精细化权限，方便人或 Agent 交互，血缘联结数据与衍生品。  
**评价**：非常好，特别是你提到了“Agent 交互”和“数据与衍生物之间的血缘”。这正是 AI 时代治理的新维度。

**补充和深化**：
- **Catalog 需要从“被动查询”转向“主动语义理解”**：传统 Catalog 存列名、类型、注释。AI 时代需要存储更多**机器可读的语义信息**：列的统计分布、embedding 映射、业务术语标签、数据质量评分、新鲜度等。这让 LLM Agent 在生成查询时能做出更合理的选择。
- **血缘需要覆盖到模型和特征**：数据→特征→模型→推理结果，整个 DAG 的血缘要打通。否则当某个底层数据出现偏差，无法快速定位影响了哪些模型和业务决策。这是比传统 ETL 血缘更深的需求，而且直接关联 AI 治理和合规。
- **跨地域权限**你说到了，但更重要是 **“数据共享不做物理拷贝”** 的能力（Delta Sharing、Iceberg 的开放表格式共享）。经济学上，这极大降低了数据交换的交易成本，让数据能够在组织间像“API 经济”一样流动，但又不失去控制。
- 这一层是**人机共同消费者**的入口，需要同时提供 UI、REST API 和自然语言接口。这种多模态访问模式是变化较快的表面层，但底层的元数据模型、权限模型必须保持稳定和开放。

**结论**：第 3 层是**信任和效率的基石**。在 AI 让数据使用门槛降低的同时，必须有更强的治理来防止“垃圾进、垃圾出”且能追溯责任。这是典型的“互补品”逻辑——AI 越强，治理越贵。

**你的描述**：存算分离下需要近计算层的加速，包括 cache 以及其他服务。  
**评价**：抓住了物理瓶颈——数据供给速度跟不上 GPU/CPU。但可以更结构化地定义这一层。

**建议细化**：
- 这是一个**横向切片**，不是独立的一层。加速策略分散在存储格式、调度、网络和本地缓存中。
- 具体形态包括：
  - **文件级/块级缓存**：Alluxio、JuiceFS 等分布式缓存，把热数据拉到计算集群本地 SSD。
  - **列统计与索引**：Parquet 的 min/max 统计、Bloom filter、Iceberg 的排序和分区进化，都是为了跳过无关数据。
  - **物化视图/预计算**：对于高频的聚合、特征变换，提前跑批存为增量物化视图，推理时直接拉取亚秒级结果。这是流批一体在加速层的体现。
  - **向量索引与近似检索**：对非结构化数据产生的 embedding，用 FAISS、ScaNN 等构建近似最近邻索引，部署为低延迟服务。
- 你在前面提到 “cold start 变重要”、“QPS 变多”、“单次查询耗时变化”，对应的解就是这一层。**它变化较快**，因为具体的缓存策略、索引算法会随硬件（CXL 内存、DPU）和模型需求演进。但底层原则不变：**空间换时间、利用数据访问局部性、减少不必要的数据移动**。

**战略建议**：这一层应该采用模块化、可插拔架构，而不是与计算引擎紧耦合，因为它是性能和成本的直接调节阀门。

---

### 第 4.2 层：统一计算引擎层
**你的描述**：能处理结构化、半结构化、非结构化数据，并能把非结构化处理结果与其他数据联合分析。  
**评价**：捕捉到了关键需求。但“统一计算引擎”这个词需要谨慎定义，因为历史上所谓“万能引擎”往往臃肿低效。

**校准理解**：
- 统一不是指一个引擎用 SQL 干所有事，而是指**一个治理和抽象框架下的多引擎协同**。
- 实际架构可能是：
  - 以 Spark/Flink 处理大规模 ETL 和流计算（结构化/半结构化）。
  - 以 Python + Ray/Dask 等分布式框架处理非结构化的预处理、embedding 生成。
  - 以 Presto/Trino 做联邦查询，跨不同源（表、向量库、传统数据库）进行联合分析。
  - 以专门的向量数据库（Milvus, Qdrant）或 Lakehouse 内的向量索引插件提供快速相似搜索。
- 你提到的“处理非结构化数据之后，对结果与其他结构化数据合并处理”，这正是**特征工程平台（Feature Engineering + Feature Store）**的职责。它需要把原始数据（图片、文本）变成结构化的特征向量，然后和用户属性、交易记录等一起作为训练/推理的输入。  
  **关键难点**在于：如何保证离线训练和在线推理的特征逻辑完全一致（时点正确、无泄漏），这需要在计算引擎层和存储层有良好协调。你列出的第 2 层（Iceberg 等）和第 4.2 层必须协同解决这一点。

**补充一个你遗漏的“第 4.3 层”**：**数据消费与交互层**。  
它是真正面向 AI Agent 和人的接口，包括：
- 自然语言查询转换为逻辑计划。
- 数据自动探查和可视化建议。
- 数据文档、指标平台的 API 化。  
这层变化最快（LLM 能力月月迭代），不适合作为“不变”的投资重点，但必须保持开放接口，能与底层解耦。

## 你的分层框架优化版

结合以上校准，我建议把你的分层重新梳理为 **五层一翼**，更清晰地反映“变与不变”的分布：

| 层次 | 核心职责 | 变化速度 | AI 时代新增重点 |
|------|----------|----------|----------------|
| **L0: 开放数据表示层** | Arrow, Parquet 格式标准，零拷贝 | 极慢 | 为 GPU 友好的列式访问、压缩算法适配 |
| **L1: 版本化数据集管理层** | Iceberg/Delta/Hudi，管理表、文件、流、特征的快照、ACID、时间旅行 | 慢 | 统一抽象覆盖非结构化文件集、特征集 |
| **L2: 治理与语义目录层** | 统一 Catalog，自动血缘，细粒度权限，跨域共享，语义标签 | 中慢（模型变，但元模型稳） | 机器可读语义、Agent 友好接口、数据合约 |
| **L3: 分布式计算与特征工程层** | 多引擎协同（Spark, Flink, Ray, 向量检索），流批一体，特征工程 | 中（引擎多样，但抽象稳定） | 训练与推理一致的特征服务，embedding 流水线 |
| **L4: 近计算加速与缓存层** | 多层缓存、物化视图、智能预取、向量索引 | 中快（硬件/算法进步） | 面向 GPU 饥饿的预取，低延迟 RAG 索引 |
| **L5: 消费者交互层** | NL2SQL, 数据探索, 指标平台, Agent 工具 | 极快 | 自然语言接口，多 Agent 协作查询 |

**“一翼”** 是贯穿各层的 **可观测性与成本计量**，这是经济学视角下不可或缺的部分。AI 大量消耗数据，必须计量哪个数据集被频繁使用、查询成本、存储成本，才能形成数据资产化的正反馈。

## 针对你最初的战略目标：在“不变”处投入

根据以上分层，你的投资重心应放在 **L0, L1, L2 的下半部分（元数据模型、权限模型、开放接口）**，以及 **L3 的特征工程与特征存储的标准抽象（保持计算引擎的可替换性）**。

- L0/L1：**事实标准不可变数据 + 版本化**，这是所有上层建筑的地基。无论 AI 怎么发展，都不可能抛弃可复现、可审计、可共享的数据事实。
- L2 稳定部分：**统一权限与血缘的元模型**（如基于 OPA 的策略引擎、OpenLineage 的血缘标准）。具体 UX 可以变，但血缘图的结构和权限模型变化很慢。
- L3 中 **Feature Store 的“特征定义与口径”** 是稳定的痛点，只要离线/在线一致性问题不消失，Feature Store 就是必须的中间层。不要绑死在一个计算引擎上，而是用标准方式定义特征，让不同引擎执行。

你不需要在 L4 具体技术选型上过早下重注（向量数据库可能重新洗牌），也无需在 L5 上自建交互模型（等待行业收敛）。保持这些层的**可插拔性**，就是对“不变”原则的最大尊重——因为你保住了底层数据资产的可移植性，未来任何加速和交互创新都能立即受益。

这样调整后，你的理解就已经非常接近工业界与经济学交叉分析下的最优策略了。

这样能避免陷入“湖仓、向量库、MCP 各讲一遍”的产品罗列。

1. 一个更完整的 Data Infra 定义

建议按四层而非仅“存储、获取、管理”来定义：

┌───────────────┬────────────────────────────────┬────────────────────────────────────────────────────────┐
│ 层            │ 核心问题                       │ 典型能力                                               │
├───────────────┼────────────────────────────────┼────────────────────────────────────────────────────────┤
│ 数据平面      │ 数据如何存、算、传             │ OLTP/OLAP、对象存储、流、批处理、缓存、向量/图索引     │
├───────────────┼────────────────────────────────┼────────────────────────────────────────────────────────┤
│ 控制平面      │ 谁可用、是否可信、如何追责     │ Catalog、权限、脱敏、血缘、质量、成本、生命周期        │
├───────────────┼────────────────────────────────┼────────────────────────────────────────────────────────┤
│ 语义平面      │ 数据“是什么意思”、能否正确组合 │ 指标定义、业务实体、schema、知识图谱、数据产品、元数据 │
├───────────────┼────────────────────────────────┼────────────────────────────────────────────────────────┤
│ 消费/接口平面 │ 消费者怎样发现、获取和操作数据 │ SQL/API、搜索、RAG、工具调用、MCP、Agent memory        │
└───────────────┴────────────────────────────────┴────────────────────────────────────────────────────────┘

传统 Data Infra 已经有前三层，只是语义平面常不完整，接口平面主要面向人和程序。LLM/Agent 使后两层成为核心竞争点。

2. 哪些不变，哪些真正变化

**不变的约束：**可靠性、延迟、吞吐、成本、安全、合规、可迁移性、数据质量、灾备。这些不会因为 AI 消失；模型基于错误、过期或越权的数据，只会更高效地产生错误。

变化的重点：

 1. 消费者从“人”转为“程序化、并发、可自主行动的 Agent”
 不只是 QPS 可能增加。更本质的是一个用户请求会扩展成多次检索、重排、数据库查询、工具调用和写操作；负载从“单次查询”变为“有状态的工作流”。需关注并发、扇出、重试、幂等、预算、审计与限流。
 2. 接口从“返回数据”转为“交付可用上下文与可执行能力”
 人可阅读仪表盘并自行判断；Agent 需要机器可发现的 schema、字段说明、权限边界、时效、血缘、示例和工具契约。MCP 是一种工具连接协议，但不是 Data Infra 本身。
 3. 语义成为基础设施的一部分
 “AI 能理解的关系”不是把所有东西做 embedding。它至少包括：  
 - 业务实体与关系：客户—订单—合同；  
 - 指标口径：GMV、活跃用户的定义和适用范围；  
 - 物理与逻辑映射：表/字段/文档片段对应的业务概念；  
 - 可信属性：owner、更新时间、质量 SLA、敏感级别、血缘、访问策略。
 LLM 擅长用自然语言匹配语义，但不能替代明确的事实、约束和授权。
 4. 检索成为新的关键路径
 SQL 仍适合精确过滤、聚合和事务；向量检索适合语义召回；图适合多跳关系；关键词/BM25 适合精确术语。实际系统通常是 metadata filter + keyword/vector hybrid retrieval + rerank + 结构化查询/工具调用，而非“用向量库替换数据库”。
 5. 治理对象扩大
 从数据治理扩展到“数据—embedding—索引—prompt/context—tool call—模型输出—Agent action”的全链路治理。尤其要能回答：某个回答引用了什么版本的数据？为何允许这个 Agent 看到它？它执行了什么动作？

3. 对你几个具体问题的判断

数据量会变大还是变小？
两者同时成立，需拆分看：

 - 原始多模态数据、日志、Agent trace、版本化索引通常变大；
 - 单次推理真正送进 context window 的数据应更小、更相关，因为 token 成本和注意力都是稀缺资源；
 - 所以目标不是“把更多数据塞进模型”，而是“以更低成本找出最可信、最小充分的上下文”。

cold start 和单次查询耗时会更重要吗？
会，但分场景：交互式 Copilot 关注首 token 和 p95 延迟；后台 Agent 更关注任务成功率、总成本、可恢复性。冷启动可能来自模型、GPU、索引、权限上下文和长链路工具连接，不能只用数据库 query latency 衡量。

多模态统一处理意味着什么？
不是所有模态存成同一格式。统一的是：对象身份、元数据、权限、版本、血缘、检索入口和关联关系。
文本通常按 chunk + embedding 使用；图像/音频/视频保留原文件并抽取转录、OCR、时间轴、标签、视觉 embedding；结构化数据仍应优先由 SQL/指标层提供确定性答案。

近推理侧计算与异构算力？
值得单列为一个主题。关键是把高频、轻量且与上下文紧耦合的工作靠近推理路径：embedding、检索、rerank、缓存、tokenization、权限过滤、结构化结果压缩。通常是 CPU/内存承担过滤与检索，GPU/NPU 承担 embedding、rerank 和生成；是否融合取决于数据位置、网络开销、并发、模型大小和成本，而不是“AI 一定需要 GPU 化数据库”。

4. 推荐的调研框架

建议选择 3 个具体 workload，而不是泛谈“AI 对 Data Infra 的影响”：

 1. 企业知识问答/Research Agent：非结构化数据、RAG、文档治理、权限继承、引用和评测。  
 2. 数据分析 Agent：自然语言到指标/SQL、语义层、结构化事实校验、查询沙箱与成本控制。  
 3. 执行型业务 Agent：读写业务系统、工具调用、审批、幂等、审计和最小权限。

每个 workload 用同一套问题比较：

 - 数据是什么，事实源是谁，更新时效要求是什么？
 - Agent 需要什么类型的 memory/context？
 - 哪些环节必须确定性，哪些可由概率模型处理？
 - 检索、计算、推理分别在哪里发生？
 - 权限如何在源头、索引、context、工具调用中持续生效？
 - 如何评估：任务成功率、事实正确性/可追溯性、p95 时延、每任务成本、越权率、人工介入率？

这会自然导出架构差异，也能检验“Agent 数量更多，因此 QPS 更高”这个假设：它可能成立，但真正应测的是每个业务任务的调用扇出、token、检索次数、写操作和失败重试。
